# 📚 Book Expert

Приложение с RAG-агентом для загрузки и поиска книг. Всё собирается и запускается в Docker.

## Запуск
```bash
# Клонировать репозиторий и перейти в каталог
git clone https://github.com/Alexandrqwerty/book-project_rag_agent.git
cd book-project_rag_agent

# Создать .env и заполнить DEEPSEEK_API_KEY и OPENROUTER_API_KEY
cp .env.example .env

# Собрать и запустить контейнеры
docker compose up --build
```
В PowerShell вместо `cp` можно использовать `Copy-Item .env.example .env`.
Ключ DeepSeek нужен для обогащения и рекомендаций. Ключ OpenRouter обязателен
для эмбеддингов и реранкинга.

Для первой сборки нужен доступ к реестру Docker и репозиториям пакетов;
для обработки книг и поиска — к API DeepSeek и OpenRouter.

**Приложение:** [http://localhost:5000](http://localhost:5000).

Docker Compose автоматически создаёт том для данных Qdrant. При запуске backend
ожидает доступности базы и создаёт отсутствующую коллекцию `books_nemotron3_2048`:
`dense-vector` (2048 чисел, Cosine).
При повторном запуске проверяется совместимость настроек; книги сохраняются.
При несовместимой схеме запуск завершается с объяснением проблемы, без удаления данных.
Размерность 2048 соответствует текущей конфигурации embedding-модели; при её замене
нужно согласованно изменить схему и переиндексировать данные.
После запуска загрузите `books.json` из корня репозитория через веб-интерфейс:
это исходный каталог из 47 книг. Подготовка коллекции сама по себе не загружает
и не обогащает книги. `books_mini.json` содержит ещё пять книг для отдельной
пробной загрузки.

Данные Qdrant хранятся в Docker-томе `qdrant_data` и сохраняются при пересоздании
контейнеров. Для остановки с сохранением базы используйте `docker compose down`.
Команда `docker compose down -v` удаляет том и все книги, описания и векторы.
При первом запуске на другом компьютере база пустая: загрузите каталог заново
либо восстановите ранее подготовленный снимок Qdrant.

## Как устроено приложение

В Docker Compose два сервиса: `backend` и `qdrant`.
Flask в `backend` отдаёт страницу, стили и JavaScript, а также принимает
запросы поиска и загрузки. В браузере всё работает через один адрес
`http://localhost:5000`:

| Маршрут | Назначение |
| --- | --- |
| `GET /` | Страница поиска |
| `GET /static/style.css` и `/static/app.js` | Стили и поведение страницы |
| `POST /chat` | Отдельный поисковый запрос: JSON с полем `message` |
| `POST /upload_books` | Загрузка каталога: multipart-файл в поле `file` |

Предыдущие запросы отображаются на странице, но не передаются агенту
как история диалога. Каждый поиск выполняется независимо.

Интерфейс использует тёмную палитру и адаптивную компоновку: боковая панель
на широком экране превращается в компактную шапку на телефоне. Примеры запросов
подставляют текст в поле, не отправляя его автоматически. Рекомендации
отображаются карточками с оговорками модели; загрузка, поиск и ошибки имеют
отдельные состояния. Учтены `prefers-reduced-motion`, видимая высота экрана
при появлении клавиатуры и безопасные отступы смартфонов. Внешние шрифты
и UI-библиотеки для страницы не нужны.

Некорректный запрос возвращает JSON с полем `error` и статусом 400;
ошибка сервиса поиска или некорректный ответ модели — 503; непредвиденный
сбой обработчика — 500. Завершённая обработка каталога возвращает статус 200
и подробный отчёт, даже если отдельные книги завершились ошибкой. Интерфейс
различает полный успех, частичный результат и неудачу. Подробности серверных
сбоев записываются в журнал backend.

Код приложения включается в Docker-образ. После изменения кода повторите
`docker compose up --build`. Для локального запуска backend из корня
репозитория используйте `python -m backend.app` при установленных зависимостях,
заполненном `.env` и доступном Qdrant на `localhost:6333`.

## Как выполняется поиск

Обогащение и рекомендации выполняет `deepseek-flash` через DeepSeek API
(`https://api.deepseek.com`), с отключённым режимом рассуждений.
Официальный API DeepSeek не предоставляет модель эмбеддингов: для векторов
используется `nvidia/nemotron-3-embed-1b:free` через OpenRouter
(`https://openrouter.ai/api/v1`), размерность 2048. Оба клиента используют
библиотеку `openai`, но разные ключи и адреса.
Для книги передаётся `input_type=passage`, для запроса — `input_type=query`;
префиксы вручную не добавляются. Бесплатные endpoints OpenRouter имеют ограничения частоты запросов.

Выбор модели для генерации задан в `backend/upload.py` константой `LLM_MODEL`;
её используют и обогащение, и финальный ответ. JSON-режим финального ответа
дополняет серверную проверку ID и структуры.

Граф LangGraph задаёт обязательную последовательность:

1. Запрос превращается в dense-вектор той же функцией и моделью, что и книги.
2. Qdrant возвращает до 20 кандидатов; реранкер оставляет до пяти.
3. LLM получает запрос, исходные и обогащённые описания и выбирает рекомендации.
4. Сервер проверяет ID выбранных книг и формирует ответ с названиями и авторами
   из каталога. Неизвестные и повторные ID отклоняются.

Отдельного вызова LLM для решения «нужен ли поиск» нет. Если база не вернула
книг, генерация ответа не вызывается. Ошибки эмбеддингов, базы, реранкера и
генерации передаются как ошибки сервиса, а не как отсутствие результатов.

Модель может выбрать меньше пяти книг или ни одной, если описания не подтверждают
соответствие запросу. Ответ запрашивается в JSON; нарушение формата даёт ошибку.
Проверка ID ограничивает список рекомендаций найденными книгами, но достоверность
свободного текста объяснений требует отдельной оценки. Обогащение тоже может
содержать ошибки: в промпте исходному описанию отдан приоритет.

### Реранкинг

Рабочая схема приложения — **20 → 5 → LLM**. В `.env.example` реранкер
включён через `RERANK_ENABLED=true`; он использует тот же `OPENROUTER_API_KEY`,
что и эмбеддинги. `RERANK_MODEL` по умолчанию —
`nvidia/llama-nemotron-rerank-vl-1b-v2:free`.

**Возможность отключения оставлена для разработки и будущих экспериментов:**
например, чтобы сравнить качество, задержку и расход ресурсов с обычным
dense-поиском. При `RERANK_ENABLED=false` Qdrant передаёт до пяти ближайших
книг напрямую в LLM. Это альтернативный режим для сравнения; при обычном
запуске по инструкции используется реранкер.

Приложение не выбирает режим автоматически. Ошибка включённого реранкера
возвращается пользователю; автоматического перехода к dense-результатам нет.

Поиск и индексация используют только dense-векторы. Дополнительные векторы
в существующей коллекции допускаются, но не участвуют в поиске и не пересчитываются.
Порог релевантности не настроен: ближайшие векторы не обязательно означают
подходящие книги. Окончательный выбор делает LLM по переданным описаниям.
Локальные автоматические тесты используют замены внешних моделей;
смысловое качество отдельно проверяли реальными API-вызовами.

## Оценка качества

На каталоге из 47 книг сравнили **20 → 5 → LLM** и **20 → 10 → LLM**:
одинаковые 20 кандидатов dense-поиска, одна ранжировка реранкера, но разное
число книг на входе финальной модели. Проверили 15 согласованных запросов:
названия, авторов, темы, ограничения по году и случаи без подходящих книг.
Оценивали полноту кандидатов, точность и полноту финального списка,
корректность отказов; объяснения модели дополнительно разбирали вручную.
Основанием служили только поля базы, включая обогащённые описания.
Частичные совпадения допускались с явной оговоркой.

**Оставили 20 → 5:** увеличение контекста до десяти книг не показало
устойчивого улучшения, но требовало больше входных токенов. В сравнении
с текущим промптом средний вход LLM составлял около **2306 токенов для пяти
книг против 3857 для десяти** — примерно на 67% больше. Это расход входных
токенов, а не измеренная разница полной стоимости или задержки запроса.

Двадцать кандидатов дают запас для отбора реранкером, а пять ограничивают
контекст финальной модели; она может рекомендовать меньше пяти книг.
Число 20 отдельно не оптимизировали. Выборка небольшая и использовалась
также для настройки промпта, поэтому выбранная схема — рабочий компромисс
для этого каталога, а не доказанный оптимум. Повторные ответы и включение
рассуждений LLM также проверяли; убедительного преимущества рассуждений
не обнаружили, в приложении они отключены.

## Правила загрузки каталога

Принимается массив книг или объект `{"books": [...]}`. Каталог должен содержать
хотя бы одну книгу. У каждой книги обязательны непустые строки `title`, `author`,
`category`, `description` и целое число `year` (строка `"1869"` и `true` не подходят).
Лишние поля игнорируются. Весь каталог проверяется до обращений к Qdrant и моделям;
при ошибке API возвращает статус 400 с номером записи и названием поля.

Произведение определяется парой «название + автор». Для сравнения выравниваются
Unicode-представление, пробелы и регистр. Новые книги получают постоянный UUID,
вычисленный из этой пары. Год, категория и описание не влияют на ID.
Правило рассчитано на произведения, а не отдельные издания; псевдонимы,
сокращения имён и альтернативные названия автоматически не сопоставляются.

Повторения одной книги внутри файла объединяются: последнее вхождение по
нормализованным названию и автору заменяет предыдущую запись целиком.
Это правило действует и при разных описании, категории или годе; поля из
разных версий не смешиваются. Порядок в файле определяет выбор, но не доказывает,
что последнее описание качественнее. До завершения проверки и объединения
всего файла обращения к базе и моделям не выполняются. Некорректная структура
или обязательные поля по-прежнему приводят к отклонению всего файла.
Старые книги с числовыми ID распознаются по названию и автору, их ID сохраняются.
При поиске существующих книг просматриваются все страницы коллекции.

### Повторная загрузка и восстановление

В payload каждой успешно обработанной книги сохраняется объект `indexing`:

- `source_hash` — SHA-256 нормализованных исходных полей книги;
- `enrichment_version` — отпечаток модели и промпта обогащения;
- `text_hash` — отпечаток полного текста, переданного на векторизацию;
- `dense_version` — версия embedding-модели и формата поискового текста.

ID отвечает на вопрос «какая книга», а `source_hash` — «изменились ли её данные».
Перед пропуском записи также сверяются реальные поля payload, наличие описания,
размерность dense, конечность чисел и ненулевой dense.
Эти проверки подтверждают техническую целостность, но не смысловое качество поиска.

| Состояние | Действие |
| --- | --- |
| Новая книга | Обогащение, dense-вектор, сохранение |
| Те же данные, версии и корректный вектор | Пропуск без вызовов моделей |
| Изменились исходные данные или версия обогащения | Новое описание и dense-вектор |
| Отсутствует/некорректен dense-вектор | Пересчёт вектора при актуальном описании и метаданных |
| Изменилась версия embedding | Пересчёт dense-вектора |
| Старая запись без версий | Однократная полная переиндексация с сохранением ID |
| Несколько записей одной книги | Выбор последней по `created_at`, обычная проверка и обработка; затем удаление остальных копий |

### Время записи и дубли

Новые записи получают `created_at` — время первого сохранения, и `updated_at` —
время последней записи данных. Даты сохраняются в ISO 8601 с часовым поясом UTC.
Обновление описания или вектора сохраняет прежний `created_at`;
пропуск актуальной книги не меняет ни одну дату.
У старых записей время создания неизвестно: при обновлении `created_at`
остаётся `null`, а `updated_at` фиксирует текущее обновление.

При загрузке книги с дублями (одинаковые нормализованные название и автор)
сначала выбирается запись с самым поздним корректным `created_at`.
Записи без даты или с некорректной датой считаются более ранними.
При равных датах либо отсутствии дат у всех копий предпочтение отдаётся
вычисляемому UUID книги, затем максимальному строковому представлению ID.
Этот запасной порядок только делает выбор стабильным и не определяет возраст записи.

Выбранная запись проходит обычную проверку по таблице выше; её ID сохраняется.
Остальные копии удаляются после успешного обновления или подтверждения,
что выбранная запись уже актуальна. При сбое обогащения, векторизации или
сохранения дубли не удаляются. Сбой удаления отражается в отчёте;
повторная загрузка повторяет очистку. Очистка касается только книг из
загружаемого файла, а не всего каталога при запуске.

При изменении формата поискового текста нужно увеличить `TEXT_VERSION` в
`backend/upload.py`. Embedding-модель задаётся там же через `DENSE_MODEL`;
поисковые запросы используют ту же функцию векторизации. При замене модели
нужны переиндексация книг и проверка размерности коллекции в `backend/storage.py`.

Каждая книга записывается отдельно, после подготовки и проверки dense-вектора.
При ошибке подготовки прежняя запись сохраняется; остальные книги продолжают
обрабатываться. Нулевые векторы и подмена описания при сбое API больше не создаются.
Если модель сама вернула исходное описание согласно промпту, это допустимый ответ.
При сетевом сбое во время записи результат может быть неизвестен: повторная загрузка
проверит запись по прежнему ID и не создаст дубликат.

Успешные книги остаются в базе даже при сбое на последующих. Промежуточные результаты
неуспешной книги отдельно не сохраняются: её незавершённые шаги при повторе могут
потребовать новых вызовов моделей. Загрузки сериализованы блокировкой внутри одного
процесса Flask; для нескольких процессов/контейнеров нужна общая координация.

Текст для эмбеддингов передаётся целиком. Отказ API,
в том числе из-за длины входа, записывается как ошибка конкретной книги. Локальный
подсчёт токенов перед запросом эмбеддингов пока не реализован.

### Отчёт загрузки

`POST /upload_books` возвращает `total` (число уникальных книг после проверки),
`added`, `updated`, `repaired`, `skipped`, `failed`, `duplicates_removed`, человекочитаемое `message`
и массив `errors` с полями `title`, `author`, `stage`, `error`.
Сумма пяти счётчиков результатов равна `total`. `duplicates_removed` — отдельное
число удалённых лишних записей, в эту сумму не входит.

Также возвращаются `input_total` — число записей в файле до объединения,
`file_duplicates` — повторы без изменения данных и `file_conflicts` — замены
с изменёнными описанием, категорией или годом. Каждый повтор сравнивается с
предыдущим вхождением той же книги. Например, описание A → B → B даёт одну
конфликтующую замену и один одинаковый повтор; в обработку попадёт только B.
`input_total = total + file_duplicates + file_conflicts`. Эти счётчики относятся
к входному файлу, а `duplicates_removed` — к очистке самой базы.

Поле `status`: `success` — ошибок нет, `partial` — ошиблась часть книг,
`failed` — ошиблись все книги. `stage` указывает этап: `lookup`, `enrichment`,
`dense`, `save` или `deduplication`. При ошибке удаления выбранная книга
может быть уже обновлена; оставшиеся дубли можно убрать повторной загрузкой.
Служебные подробности исключений доступны в журнале;
интерфейс показывает понятное сообщение и название книги.

## Автоматические проверки

### Линтер Ruff

В Python-окружении для разработки установите зависимости:

```bash
python -m pip install -r requirements-dev.txt
```

Из корня проекта запустите проверку:

```bash
python -m ruff check .
```

Версия Ruff закреплена в `requirements-dev.txt`; настройки находятся в
`pyproject.toml`. Проверяются `.py`-файлы приложения и тестов:
базовые ошибки Python/Pyflakes (`E4`, `E7`, `E9`, `F`) и порядок импортов (`I`).
Ruff — инструмент разработки: Docker устанавливает только `requirements.txt`.

### Тесты

В Python-окружении с установленными зависимостями:

```bash
python -m unittest discover -s tests -v
```

Проверки используют локальный режим Qdrant без сервера, Flask test client и
тестовые замены моделей; API-ключи и загрузка весов не нужны. Проверяются
подготовка коллекции, сохранность старых записей, формат каталога, постоянство ID,
повторная загрузка, выборочное восстановление векторов, изменение версий,
сохранность данных при сбоях, чтение всех страниц коллекции и HTTP-отчёты об ошибках.
Также проверяются обязательный поиск перед генерацией, передача описаний модели,
проверка ID рекомендаций, ключ и формат ответа реранкера, различие между пустым
результатом и сбоем. Локальная интеграционная проверка проходит путь
«HTTP-загрузка → индексация → Qdrant → граф поиска → HTTP-ответ» с заменами моделей.
